# Braverave Escalation Guard — дизайн

Дата: 2026-09-01
Статус: утверждён к реализации

## 1. Задача

В воркспейсе Slack `braverave` саппорт OlasBet шлёт эскалации операторам в три канала.
Одни и те же запросы попадают в канал повторно, а часть эскалаций зависает без ответа.
Нужен бот, который ловит дубликаты в момент публикации и напоминает про зависшие запросы.

Каналы и их правила:

| Канал         | Дубликат по    | Трекинг «7 дней без решения» |
|---------------|----------------|------------------------------|
| `#2-payments` | Transaction ID | да                           |
| `#7-bonuses`  | Player ID      | нет                          |
| `#3-kyc`      | Player ID      | нет                          |

Окно проверки дубликатов везде 7 дней. Ограничение принципиальное: по одному игроку
законно бывают разные эскалации в разное время, без окна бот превратится в шум.

Реакции задают статус:

- `:eyes:` — взяли в работу, но не закрыли;
- `:white_check_mark:` — решено.

Только `:white_check_mark:` считается решением. `:eyes:` на трекинг висяков не влияет.

## 2. Форматы сообщений

`#2-payments`:

```
Player ID: 688087847
Transaction ID: 700000001779189773
Type: Deposit
Amount and Currency: 4 000 ARS
Issue: a different amount
```

`#7-bonuses`:

```
Player ID: 743080300
Promo / bonus: FreeSpins/FreeBet for Deposit with Wagering Bonus
Issue / need: The customer did not receive the bonus after making a deposit.
```

`#3-kyc`:

```
Player ID: 439545299
Document + status: Uploaded
Issue: Long verification process
```

Общий якорь во всех трёх — строка `Player ID:` с числом. Метки приходят в mrkdwn
жирным (`*Player ID:*`), к вложениям и скриншотам бот безразличен.

## 3. Архитектура

Одно внутреннее Slack-приложение на весь воркспейс, один процесс на VPS (Linux),
Socket Mode, три канала описаны в конфиге. Состояние — локальная база SQLite,
работающая как индекс сообщений и реакций.

Ключевое решение: **проверка дубликата не ходит в Slack API**. Бот строит индекс
из событий в реальном времени и при старте догоняет 7 дней истории. Проверка
дубля — один SELECT, ответ в тред за доли секунды.

```
Slack (Socket Mode)
  |- message.channels ---|
  |- reaction_added -----+--> handlers.py --> db.py (SQLite)
  |- reaction_removed ---|                       |
                                                 |
  backfill.py (при каждом старте, 7 дней) -------|
  sweeper.py (ежечасно, висяки payments) --------|
                          |
                          `--> chat.postMessage в тред
```

### 3.1 Структура проекта

```
config.py      каналы, окна, эмодзи, шаблоны текстов
parser.py      извлечение Player ID / Transaction ID
db.py          схема SQLite и запросы
handlers.py    message / message_changed / reaction_added / reaction_removed
backfill.py    догон истории при старте
sweeper.py     ежечасный проход по висякам
main.py        сборка: backfill -> планировщик -> Socket Mode
tests/         pytest
deploy/        systemd unit, пример .env, манифест приложения
```

## 4. Схема данных

Таблица `escalations`, первичный ключ `(channel_id, ts)`:

| поле                 | назначение                                  |
|----------------------|---------------------------------------------|
| `channel_id`         | канал                                       |
| `ts`                 | Slack timestamp сообщения                   |
| `user_id`            | автор эскалации, нужен для пинга            |
| `created_at`         | float-время публикации                      |
| `player_id`          | распарсенный ID игрока, может быть NULL     |
| `transaction_id`     | распарсенный ID транзакции, может быть NULL |
| `text`               | обрезанный текст, для отладки               |
| `duplicate_notified` | 0/1, ответ про дубль уже отправлен          |
| `stale_notified`     | 0/1, напоминание про 7 дней уже отправлено  |

Таблица `reactions`, первичный ключ `(channel_id, ts, name, user_id)`.
Отдельная таблица, а не флаг на сообщении: `:white_check_mark:` могут поставить
двое, и снятие реакции одним не должно обнулять статус. Она же даёт список тех,
кто поставил `:eyes:` — их пингует sweeper.

Признак «решено» нигде не хранится, а выводится запросом «существует ли реакция
из `RESOLVED_EMOJI`». Один источник правды, рассинхрону взяться неоткуда.

Индексы: `(channel_id, transaction_id, created_at)`, `(channel_id, player_id, created_at)`,
`(channel_id, created_at)`.

Таблица `meta` — пары ключ/значение, хранит время последнего успешного бэкфилла.

Retention: записи старше 30 дней удаляются ежедневно. Окно работы 7 дней, остальное
запас на ручной разбор.

## 5. Парсер

Нормализация текста: снимаются mrkdwn-символы `*`, `_`, backtick; неразрывные
пробелы заменяются обычными; последовательности пробелов схлопываются.

Извлечение, регистронезависимо:

- `player\s*id\s*[:\-]?\s*(\d{4,})`
- `transaction\s*id\s*[:\-]?\s*(\d{6,})`

Берётся первое совпадение.

**Допущение:** одно сообщение содержит не более одной транзакции. Если регэксп
находит несколько Transaction ID, берётся первый и пишется WARNING в лог. Если
в проде такое всплывёт, схема расширяется таблицей «много ID на сообщение».

Не обрабатываются:

- ответы в тредах (`thread_ts` присутствует и не равен `ts`);
- сообщения от ботов (наличие `bot_id`), включая собственные;
- служебные subtype (`channel_join`, `channel_leave` и подобные).

`message_changed`: текст перечитывается и ID обновляются. Если Transaction ID
изменился, а `duplicate_notified = 0`, проверка дубля запускается заново.
Повторный ответ на одно и то же сообщение исключён флагом.

`message_deleted`: запись удаляется из `escalations` вместе со связанными
реакциями. Иначе удалённая эскалация продолжала бы порождать ложные срабатывания
дубля, а sweeper через неделю написал бы напоминание в несуществующий тред.

Сообщение без нужного ID всё равно сохраняется — оно участвует в трекинге висяков,
но не в сверке дублей.

## 6. Обработка нового сообщения

1. Распарсить, сделать upsert в `escalations`.
2. Взять правило канала из конфига: `payments` сверяет `transaction_id`,
   `bonuses` и `kyc` — `player_id`.
3. Если нужный ID пуст, остановиться.
4. Найти в том же канале сообщения с тем же ID за последние 7 дней, исключая себя.
5. Совпадений нет — бот молчит. Это осознанное требование: тишина при отсутствии
   дубля, иначе каналы зарастают.
6. Совпадения есть — один ответ в тред нового сообщения, `duplicate_notified = 1`.

Флаг `duplicate_notified` защищает от повторной доставки события: Slack ретраит
события при отсутствии подтверждения, и без флага оператор получил бы два ответа.

## 7. Sweeper

Запуск ежечасно. Выборка: канал `payments`, `stale_notified = 0`, возраст больше
7 дней, возраст меньше 30 дней, отсутствует реакция из `RESOLVED_EMOJI`.

Для каждой найденной эскалации — одно сообщение в тред, затем `stale_notified = 1`.
Повторных напоминаний не бывает.

Пинги в напоминании: автор эскалации и все, кто поставил `:eyes:`. Если `:eyes:`
никто не ставил, пингуется только автор.

**Холодный старт.** При инициализации пустой базы всё, что старше 7 дней на момент
бэкфилла, помечается `stale_notified = 1`. Бот стартует с чистого листа и не
вываливает стену уведомлений на накопившийся архив. Поведение переключается
флагом `COLD_START_SILENT` в конфиге.

## 8. Тексты сообщений

Язык английский, каналы англоязычные. Ссылки на исходные сообщения берутся через
`chat.getPermalink`, а не склеиваются вручную из ts.

Дубль в `#2-payments`:

```
:warning: *Duplicate escalation*
Transaction `700000001779189773` was already escalated 2 days ago by @Mari
Status: in progress :eyes:
<permalink|Open original>
```

Возможный дубль в `#7-bonuses` и `#3-kyc`:

```
:warning: *Possible duplicate*
Player `743080300` — 2 escalations in this channel in the last 7 days:
- <permalink|Aug 28> by @Boris — resolved :white_check_mark:
- <permalink|Aug 30> by @Ilya — no reaction yet
```

Показываются максимум 3 последних совпадения, дальше строка `and N more`.
Статус каждого исходника: `resolved` при `:white_check_mark:`, `in progress`
при `:eyes:`, иначе `no reaction yet`. Оператор сразу видит, стоит ли открывать
старый тред.

Напоминание про висяк:

```
:hourglass_flowing_sand: *7 days without resolution*
No :white_check_mark: on this escalation.
Player `688087847` - Transaction `700000001779189773`
cc <@author> <@eyes_user_1> <@eyes_user_2>
```

## 9. Права и настройка приложения

Приложение внутреннее, одного воркспейса, вне Slack Marketplace. Это существенно:
лимит 1 запрос в минуту на `conversations.history`, введённый 29 мая 2025 года для
приложений, распространяемых вне Marketplace, на внутренние приложения не
распространяется — у них сохраняются 50+ запросов в минуту и до 1000 объектов.
Бэкфилл 7 дней по трём каналам укладывается в лимит без ухищрений.

Bot token scopes: `channels:history`, `channels:read`, `chat:write`, `reactions:read`.
Все три канала публичные, поэтому `groups:*` не нужны.

Подписки на события: `message.channels`, `reaction_added`, `reaction_removed`.

App-level token со скоупом `connections:write` — для Socket Mode.

Приложение создаёт владелец воркспейса на api.slack.com из подготовленного манифеста
(`deploy/manifest.yaml`). Бота нужно пригласить в три канала. Токены живут в `.env`
на VPS и в репозиторий не попадают.

## 10. Конфигурация

`.env`: `SLACK_BOT_TOKEN` (xoxb-), `SLACK_APP_TOKEN` (xapp-), `DB_PATH`, `LOG_LEVEL`.

`config.py`:

```python
CHANNELS = {
    "<C_PAYMENTS>": {"name": "2-payments", "match": "transaction_id", "stale_tracking": True},
    "<C_BONUSES>":  {"name": "7-bonuses",  "match": "player_id",      "stale_tracking": False},
    "<C_KYC>":      {"name": "3-kyc",      "match": "player_id",      "stale_tracking": False},
}
DUP_WINDOW_DAYS = 7
STALE_AFTER_DAYS = 7
RETENTION_DAYS = 30
SWEEP_INTERVAL_MINUTES = 60
MAX_DUPLICATES_SHOWN = 3
RESOLVED_EMOJI = {"white_check_mark", "heavy_check_mark"}
IN_PROGRESS_EMOJI = {"eyes"}
COLD_START_SILENT = True
```

Добавить четвёртый канал — одна строка в `CHANNELS`, без правок кода.

Плейсхолдеры `<C_PAYMENTS>`, `<C_BONUSES>`, `<C_KYC>` заполняются реальными
Slack channel ID вида `C0123ABCDEF` после создания приложения. Взять их можно
в Slack: правый клик по каналу, «Copy link», последний сегмент URL.

## 11. Деплой и эксплуатация

systemd unit с `Restart=always`, виртуальное окружение Python 3.11+, переменные из
`EnvironmentFile`, логи в journald.

Порядок запуска: бэкфилл 7 дней по всем каналам, затем планировщик, затем Socket Mode.
Бэкфилл при каждом старте означает, что перезагрузка VPS и выкатка релиза не создают
дыр в данных — пропущенные за время простоя сообщения и реакции подхватятся.

Режим `--dry-run`: бот считает всё как обычно и пишет в лог, что отправил бы, но
в Slack ничего не постит. Первые сутки эксплуатации проходят в этом режиме.

Бэкап базы: ежедневный `sqlite3 .backup`.

## 12. Тестирование

- `test_parser.py` — реальные примеры из трёх каналов, mrkdwn-жирный, лишние
  пробелы, отсутствующие поля, мусорный текст, несколько Transaction ID.
- `test_duplicates.py` — совпадение внутри окна, ровно на границе 7 дней, за
  окном; совпадение в другом канале не считается дублем; повторная доставка
  события не даёт второго ответа; правка сообщения с новым Transaction ID.
- `test_sweeper.py` — возраст меньше и больше 7 дней; наличие и отсутствие
  `:white_check_mark:`; `:eyes:` не закрывает; повторный прогон не шлёт второе
  напоминание; холодный старт молчит про старое; список пингуемых собран верно.
- `test_reactions.py` — двое поставили `:white_check_mark:`, один снял, статус
  остаётся «решено».

Тесты идут на in-memory SQLite с подставными временными метками, без обращений
к Slack API.

## 13. Что осознанно не делается

- Нет дайджестов и сводных отчётов. Только ответы в тредах.
- Нет трекинга висяков в bonuses и kyc.
- Нет реакции на совпадение по Player ID в payments — там дубль определяется
  строго по Transaction ID.
- Нет веб-интерфейса, метрик и админки.
